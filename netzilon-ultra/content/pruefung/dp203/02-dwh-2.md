- drei Spalten einer vorhandenen Zeile aktualisieren
- zwei Spalten einer vorhandenen Zeile aktualisieren

* eine Spalte einer vorhandenen Zeile aktualisieren
! Bei Typ 2 wird die alte Version abgeschlossen (nur EndDate setzen = 1 Spalte) und eine neue Zeile mit dem neuen Nachnamen eingefügt.

? DimProduct (ProductKey, ProductSourceID, ProductName, ProductDescription, Color; REPLICATE, CCI) soll eine SCD Typ 3 werden: ProductKey und ProductSourceID bleiben gleich, ProductName, ProductDescription und Color können sich ändern. Welche DREI Spalten fügen Sie hinzu?
- [EffectiveStartDate] [datetime] NOT NULL
- [EffectiveEndDate] [datetime] NOT NULL
* [OriginalProductDescription] NVARCHAR(2000) NOT NULL
- [IsCurrentRow] [bit] NOT NULL
* [OriginalColor] NVARCHAR(50) NOT NULL
* [OriginalProductName] NVARCHAR(100) NULL
! Typ 3 = für jedes veränderliche Attribut eine zusätzliche Spalte mit dem ursprünglichen/vorherigen Wert. Datumsspalten und IsCurrentRow gehören zu Typ 2.
@ DP-203 Frage 100

? Sie haben eine Lake-Datenbank aus einer Synapse-Datenbankvorlage bereitgestellt und wollen weitere Tabellen nach derselben Gruppierungsmethode wie die Vorlagentabellen hinzufügen. Welche Gruppierung?
- Partitionsstil
* Geschäftsbereich (Business Area)
- Größe
- Fakten und Dimensionen
! Die Tabellen in Datenbankvorlagen sind nach Geschäftsbereichen (z. B. Customer, Sales, Product) gruppiert.

- [EffectiveStartDate] [datetime] NOT NULL

@ DP-203 Frage 129

? Eine Datumsdimension im dedizierten SQL-Pool wird von allen Faktentabellen genutzt. Welcher Verteilungstyp minimiert die Datenverschiebung?
- HASH
* REPLICATE
- ROUND_ROBIN
! Replizierte Tabellen liegen auf jedem Compute-Knoten – Joins mit Faktentabellen benötigen keine Datenverschiebung.
@ DP-203 Frage 260

? Eine 10-TB-Faktentabelle in Synapse wird über die Primärschlüsselspalte SaleKey abgefragt (Spalten CityKey, CustomerKey, StockItemKey, InvoiceDateKey, Quantity, UnitPrice, TotalExcludingTax). Sie soll für optimale Leistung auf mehrere Knoten verteilt werden. Welche Technologie?
- hashverteilte Tabelle mit gruppiertem Index
* hashverteilte Tabelle mit gruppiertem Columnstore-Index
- Round-Robin-Tabelle mit gruppiertem Index
- Round-Robin-Tabelle mit gruppiertem Columnstore-Index
- Heap-Tabelle mit Replikation
! Große Faktentabellen: Hash-Verteilung + Clustered Columnstore Index (bis 10× Komprimierung, bis 100× schnellere Analysen).
@ DP-203 Frage 291

? Ein Sternschema für Online-Bestellungen (Bestell-, Fälligkeits- und Versanddatum) soll beliebige Datumsbereiche und Aggregationen nach Geschäftsjahresattributen (Fiscal Calendar) möglichst schnell abfragen. Welche ZWEI Aktionen?
- eine Datumsdimension mit DateTime-Schlüssel erstellen
- integrierte SQL-Funktionen zum Extrahieren der Datumsattribute verwenden
* eine Datumsdimension mit ganzzahligem Schlüssel im Format YYYYMMDD erstellen
* in der Faktentabelle ganzzahlige Spalten für die Datumsfelder verwenden
! Eine Datumsdimension mit int-Schlüssel (YYYYMMDD) enthält vorberechnete Geschäftsjahresattribute; die Fakten verweisen per int (rollenspielende Dimension). Die Sammlung nennt BD, die Community (91 %) CD.
@ DP-203 Frage 303

? Die Faktentabellen Flight und Weather werden über Flight.ArrivalAirportID/ArrivalDateTime und Weather.AirportID/ReportDateTime verknüpft. Was maximiert die Abfrageleistung?
- Hash-Verteilung auf ArrivalDateTime bzw. ReportDateTime
* Hash-Verteilung auf ArrivalAirportID bzw. AirportID
- in jeder Tabelle eine IDENTITY-Spalte erstellen
- in jeder Tabelle eine zusammengesetzte Spalte aus den beiden anderen erstellen
! Beide Tabellen auf der Join-Spalte hashverteilen → verteilungskompatible Joins ohne Datenverschiebung. Datumsspalten eignen sich nicht als Verteilungsschlüssel.
@ DP-203 Frage 311

## Zuordnen

### DP-203 Frage 73 (Hotspot): Tabelle Country (195 Zeilen) und Tabelle Sales (100 Mio. Zeilen: OrderDate, CustomerId, CountryId, Total); Abfrage: Gesamtumsatz je Land und Kunde der letzten 30 Tage. Abfrageleistung maximieren.
- DISTRIBUTION für Sales => HASH([CustomerId])
- DISTRIBUTION für Country => REPLICATE

### DP-203 Frage 75 (Hotspot): Datenmodell db1 (serverlos) mit FactOrders, Date, DimCustomer, DimGeography, DimStore, Product, ProductLine (Schneeflocke). Vervollständigen Sie die Aussagen.
- Um das Modell in ein Sternschema zu überführen => DimGeography und DimCustomer verknüpfen (join)
- Anzahl der Tabellen nach der Umwandlung in ein Sternschema => 5

### DP-203 Frage 88 (Drag & Drop): SCD „Product“ – ProductName darf sich nie ändern, für ProductSize nur aktueller und letzter Wert, für ProductColor alle aktuellen und früheren Werte. Welcher SCD-Typ je Spalte?
- ProductName => Typ 0 (unveränderlich)
- ProductColor => Typ 2 (vollständige Historie in neuen Zeilen)
- ProductSize => Typ 3 (aktueller + vorheriger Wert in Spalten)

### DP-203 Frage 89 (Hotspot): Faktentabellen werden inkrementell geladen; jeder Batch wird vorher in Stagingtabellen bereitgestellt – so schnell wie möglich.
- Tabellenverteilung der Stagingtabellen => ROUND_ROBIN
- Tabellenstruktur => Heap

### DP-203 Frage 122 (Drag & Drop): Tabelle Employees (first_name, last_name, hire_date, employee_type). employee_type soll aus hire_date berechnet werden: `SELECT *, [1] WHEN hire_date >= '2019-01-01' THEN 'New' [2] 'Standard' END AS employee_type FROM employees`
- [1] => CASE
- [2] => ELSE

### DP-203 Frage 186 (Hotspot): Faktentabelle für Website-Besuche (ca. 5 GB) in einem Synapse-Sternschema – schnellste Abfrageleistung.
- Verteilung => Hash (über 2 GB, häufige Änderungen)
- Index => Clustered Columnstore

### DP-203 Frage 215 (Drag & Drop): Batchladen aus einer Stagingtabelle in einen dedizierten SQL-Pool; bei einem Fehler sollen alle Einfügungen des Batches zurückgenommen werden. `[1]; BEGIN TRY INSERT INTO dbo.Table1 (col1, col2, col3) SELECT col1, col2, col3 FROM stage.Table1; END TRY BEGIN CATCH IF @@TRANCOUNT > 0 BEGIN [2] END END CATCH; IF @@TRANCOUNT > 0 BEGIN COMMIT TRAN; END`
- [1] => BEGIN TRAN (verteilte Transaktionen gibt es im dedizierten Pool nicht)
- [2] => ROLLBACK TRAN

### DP-203 Frage 322 (Hotspot): Migration nach Synapse – Sales (600 GB; DateKey im WHERE, ProductKey in Joins, RegionKey zum Gruppieren; 75 % der Zeilen gehören zu einer von 40 Regionen) und Invoice (6 GB; DateKey und ProductKey im WHERE, RegionKey zum Gruppieren); 120 Produkte, 65 Regionen. Abfrageleistung optimieren, Verarbeitungsschiefe minimieren. (Sammlung: Invoices hash auf RegionKey – RegionKey ist jedoch stark schief verteilt)
- Sales – Verteilungstyp => Hashverteilt
- Sales – Verteilungsspalte => ProductKey
- Invoices – Verteilungstyp => Round-Robin (keine Verteilungsspalte)
